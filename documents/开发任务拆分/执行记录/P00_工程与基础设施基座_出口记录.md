## 阶段

阶段：P00 工程与基础设施基座  
开始条件：绿地工程，无上一阶段出口依赖  
本次范围：后端空工程、15 个领域 AppConfig、三端独立前端、共享包、OpenAPI、Nginx、Kong、Compose、Swarm、数据服务、日志与指标基座；不实现业务模型、业务表、账号、Session 或业务 API。

## 数据库/schema

- 15 个领域 app 均无 model 和 migration，`makemigrations --check --dry-run` 无变更，`migrate --plan` 无操作。
- Compose 定义空 MySQL 8.4 LTS、Redis 7、MongoDB Replica Set、MinIO 和 ClamAV，并使用命名卷；MinIO 初始化 bucket 和版本控制。
- 本地容器实测 MySQL `8.4.11`，migration 退出码为 0；Redis `PONG`、MongoDB、MinIO 和 ClamAV 健康检查通过。
- `reset-p00-local-data.ps1` 可删除 P00 命名卷并从空环境重新构建；修复后冷启动复验通过。
- 预发布 Swarm 不伪造单节点数据 HA，要求外部/托管或另行评审的副本数据服务。
- 未创建 `teams` app、`teams` 表、旧角色、示例用户、教师、团队或课程。

## 后端

- 正式工程位于 `backend/education_experiment_platform`，settings 拆分为 `base/local/test/integration/prod`。
- 建立 ASGI、Celery worker 路由、统一 JSON 错误、W3C trace、结构化 JSON stdout、Prometheus endpoint、健康/就绪检查和 OpenAPI 导出。
- 固定 `/api/v2`、`/api/v2/events/stream`、`/workspace`、`/files` 路径。
- Portal/Integration 上下文只接受专用 app 网络内且带 `X-Proxy-Context: ingress-v1` 的代理请求；直接绕过代理访问非健康 API 被拒绝。
- OpenAPI 3.0.3 包含健康、就绪、SSE 及 `x-portals` 标记，TypeScript 类型由规范生成。

## 前端

- 建立 `apps/user-web`、`apps/teacher-web`、`apps/admin-web`，拥有独立入口、路由、构建产物和版本信息。
- 建立 `ui/api-client/auth-client/event-client/query-keys/config` 共享包；共享包不含业务页面或业务权限语义。
- 三端只实现登录壳、健康页、403/404/500 和错误边界；登录请求使用真实 `/api/v2/auth/login`，未使用 Mock。
- Session/Token 不写入 localStorage；E2E 已检查浏览器存储为空。

## 基础设施

- 本地入口：Nginx 三个静态 Host + 无前端机器 Host，Kong 按 Host 覆盖可信上下文头。
- 本地 Compose 运行单 Nginx 入口副本，避免宿主 `8080` 端口冲突；预发布 Swarm stack 仍保留双副本入口。
- Kong 显式限制每容器 2 个 Nginx worker；两副本在 90 次连续入口请求后均为 healthy、`OOMKilled=false`、零重启。
- Python、Node 和 Nginx 构建基础镜像及 Debian 软件源均可通过环境变量覆盖；默认开发源已在当前网络完成冷启动构建。
- 生产入口：80 跳转 443，TLS 证书来自 Swarm Secrets；配置 HSTS、CSP、nosniff、Referrer-Policy 和 Permissions-Policy。
- SSE 关闭 buffering；`/workspace` 配置 WebSocket Upgrade；管理端拒绝工作区代理；机器入口只匹配 integration token/open API。
- Swarm stack 定义 edge/app/worker/runtime/data 标签约束、Secrets、Configs、资源 reservation/limit、滚动更新和失败回滚。
- Fluent Bit 全局采集、字段/文本脱敏、磁盘缓冲后经 log-ingest 写 MongoDB `runtime_logs`；建立 TTL 及 service/level/trace/resource 查询索引。
- Fluent Bit 的 fluentd 端口仅发布到宿主 `127.0.0.1:24224`，并通过独立网络解决 Docker Desktop 对 internal 网络不发布端口的问题；日志生产者在 Fluent Bit 启动后启动。
- OTel Collector 与 Prometheus 配置完成；MongoDB 不参与 Django 健康判定。

## 兼容性阻塞

Django 6.1.1 运行时要求 MySQL 8.4 或更高，原 MySQL 8.0 架构声明无法启动 migration。架构总纲、数据库物理设计、兼容性基线和 Compose 已统一调整为 MySQL 8.4 LTS，本地实测版本为 8.4.11。

PyPI 发布的 `django-celery-beat==2.9.0` 要求 `Django<6.1`，与架构固定的 Django 6.1.1 冲突。P00 不运行 Beat，故从可执行锁文件中隔离，保留 Celery 5.6.3 worker；在上游发布支持版本或架构评审调整前不得启用 Beat。
