## 一、需求变更与业务闭环

旧模型是：

```text
加入唯一团队 → 团队管理员发布实验 → 团队成员完成实验
```

v2 模型是：

```text
管理员授予教师资格并维护平台资源
  → 教师创建和发布课程
  → 学生浏览课程并选课
  → 教师为课程发布实验
  → 系统为符合受众规则的选课记录生成个人实验任务
  → 学生完成实验、工作区操作和成果提交
  → 本课程教师审核
  → 系统归档、撤销会话、销毁实例并释放配额
```

课程是新的教学聚合根，不是 `teams_team` 的重命名。教师可负责多门课程，学生可同时选多门课程；课程之间的数据、权限、配额与 Agent 上下文必须隔离。

## 二、三个独立网页

三个端必须是三个独立 Web 应用，而不是同一 SPA 中的三个路由区：

| 应用 | 示例站点 | 主要用户 | 核心能力 |
|---|---|---|---|
| `user-web` | `user.example.edu` | 学生 | 课程目录、选课、我的课程、个人实验、工作区、报告与反馈 |
| `teacher-web` | `teacher.example.edu` | 教师 | 创建课程、名册、模板、实验发布、过程追踪、审核与成果 |
| `admin-web` | `admin.example.edu` | 平台管理员 | 账号/教师资格、课程监管、运行时、配额、实例、安全与审计 |

三个应用具有独立的 `index.html`、入口、路由树、构建产物、站点配置、测试、发布和回滚。它们共享账号数据库、后端 API、OpenAPI 规范及构建期公共包，但不共享浏览器运行时、路由状态或父域 Session Cookie。

开放 API 另使用无前端制品的机器入口 `api.example.edu`。该入口只暴露 client credential token 和明确标记的开放 API，不属于第四个前端，也不建立 Portal Session。

后端保持一套按领域划分的服务和数据库。三端拆分是交付、安全和信息架构边界，不是复制三套业务逻辑。

## 三、范围与非目标

### P0 范围

- 账号登录、学校/企业身份资料、教师资格、平台管理员资格。
- 课程创建、编辑、发布、关闭和归档。
- 开放选课与审批选课、容量控制、退课/移除及阻断检查。
- 课程教师/助教任职和课程级最小授权。
- 课程实验模板、不可变版本、预检和发布。
- 每名学生独立的实验任务、容器/虚拟机、工作区与自动保存。
- 报告/成果、课程教师审核、归档、导出和资源回收。
- 课程章节、资料、公告、日历、问答、邀请码/批量名册和课程复制。
- 学习路径与先修条件、个人延期/补交、工作区检查点和受控操作回放。
- 评分量规、定位批注、自动检查和仅作辅助判断的成果相似度分析。
- 教学分析、风险提醒、课程质量、学习建议和资源成本看板。
- 任务上下文内的受控 Agent、课程知识库、引用溯源、评测、通知、审计、补偿与观测。
- OIDC 单点登录、开放 API 和签名 Webhook；不包含 LMS 专用连接器。

### 首期不做

- 班级、专业、院系、小组和多租户组织树。
- 课程支付、学分、正式成绩单、排课和教务系统替代。
- OJ 题库、多人协同实验、模板市场和学生自由创建环境。
- 自定义角色设计器和任意权限表达式。
- 三套后端、三套数据库或跨端父域 Cookie 单点登录。
- 未经审批的 Agent 高风险写文件、执行命令、安装依赖或联网。
- Moodle、Canvas 等 LMS 的专用对接、LTI 和成绩回传。
- PWA、离线通知和单独的移动端只读模式；普通响应式网页仍需覆盖既定视口。
- 国际化/多语言切换和专项无障碍合规建设。

## 四、实际技术基线

下表是本项目首期目标基线。P00 必须据此创建并提交 `backend/COMPATIBILITY.md` 与依赖锁文件；在这些文件落库前，不把本机已安装版本或旧版文档当成实现事实：

| 层 | 基线 |
|---|---|
| 后端 | Python 3.14、Django 6.1、DRF 3.18.1、drf-spectacular 0.30.0 |
| 前端 | React 18.3、TypeScript 5.9、Vite 7、React Router 7、TanStack Query 5 |
| 数据 | MySQL 8.4 LTS、Redis 7、MongoDB（运行日志）、MinIO、ClamAV |
| 异步 | Celery 5.6、django-celery-beat 2.9 |
| 接口 | REST + OpenAPI 3.0.3、SSE、受控文件/工作区网关 |
| 入口 | Nginx Ingress + API Gateway；三个网页 Host 同源代理 `/api/v2`（SSE 固定为 `/api/v2/events/stream`）、`/workspace`、`/files`；`api.example.edu` 仅提供机器 token/open API |
| 运行 | Docker Swarm 管理平台服务；实验容器通过受控 Runtime Adapter 调度 |
| 观测 | Prometheus + OpenTelemetry + 结构化日志采集，`trace_id` 贯穿请求和异步链路 |

v2 不因业务变更升级框架；依赖升级需单独兼容性评审。

## 五、分层架构

```text
user-web       teacher-web       admin-web
    │               │               │
    └──── HTTPS / same-origin relative paths ────┐
                                                  ▼
                 Nginx Ingress / TLS / static assets
                 Host routing / request limits / SSE+WS
                                                  ▼
                 API Gateway (APISIX/Kong/Traefik)
                 API route / rate limit / timeout / trace
                                                  ▼
                 Django ASGI × N (single modular backend)
                 API → Permission → Selector/Service → Model
                    │                 │ transaction.on_commit
                    │                 ▼
                    │          Celery Worker × M / Beat × 1
                    │                 │
                    ▼                 ▼
             MySQL facts        Docker Swarm Runtime Adapter
             Redis broker/cache  Container / optional VM adapter
             MinIO objects

stdout logs → Fluent Bit/Vector/OTel Collector → MongoDB Replica Set
metrics/traces → OTel Collector → Prometheus/Grafana
```

### 5.1 入口层职责

| 层 | 负责 | 明确不负责 |
|---|---|---|
| Nginx | TLS、三站点 Host 路由、静态制品、基础限流、请求体大小、SSE/WS 转发、请求 ID | 课程/任务对象授权、业务状态、最终认证判定 |
| API Gateway | `/api/v2` 路由、版本、网关限流、熔断、超时、灰度、追踪透传、可信 `X-Portal` | 课程任职、选课、任务和审核的对象级授权 |
| Django | Session/CSRF、对象 scope、状态机、事务、幂等、审计、Outbox | 直接调用 Docker/Swarm、在请求内执行长外部 I/O |

Nginx 和 API Gateway 不重复实现业务路由。浏览器传入的 `X-Portal` 必须被 Nginx/Gateway 丢弃并由可信 Host 映射覆盖；机器入口还必须删除外部传入的认证上下文头并写入可信 `X-Auth-Context: INTEGRATION`。Django 只信任来自受控代理网络的这些头。

### 5.2 运行与状态服务边界

- Docker Swarm 默认管理 Django、Celery、Gateway、日志采集等无状态服务；实验容器是否进入 Swarm 由 `RuntimeAdapter` 决定，不能由 Web 进程直接创建。
- MySQL、MongoDB、Redis、MinIO 的持久卷不能依赖单个 Swarm 节点本地目录。生产部署必须选择外部托管、分布式卷或明确的副本/故障切换方案。
- Swarm 的 CPU/内存 reservation/limit 只执行运行时约束；平台、课程、用户配额的事实仍在 MySQL。
- Redis 可丢失并可从 MySQL 重建；MongoDB 只存运行日志，不承载业务审计和状态事实。

### 分层纪律

1. View/Serializer 不推进状态；所有业务写入由 service 执行。
2. Worker 调用同一 service，不直接裸改模型状态。
3. Web 请求不直接执行 Docker、libvirt、归档或模型推理。
4. selector 是数据范围的唯一查询入口；不可见对象返回 404。
5. MySQL 是事实源；Redis 可丢失并能从 MySQL 重建。
6. 三个 Web 的路由守卫只改善体验，不构成权限边界。

## 七、跨切面约束

所有不可逆或有并发风险的写操作必须同时具备：

| 机制 | 规则 |
|---|---|
| 权限 | 门户准入 + 全局资格 + 课程对象 scope + 当前状态四层校验 |
| 状态 | 集中状态机，非法跃迁返回稳定错误码 |
| 幂等 | `Idempotency-Key` + actor/endpoint/request digest 唯一记录 |
| 并发 | `row_version`/`If-Match`；容量、负责人和状态机使用行锁 |
| 审计 | actor、portal、course、动作、脱敏前后值、结果、trace_id |
| 事件 | 业务事实和 Outbox 同事务；至少一次投递，消费者幂等 |
| 只追加 | 选课事件、任务跃迁、报告版本、审核结论、归档清单和审计不可覆盖 |

## 八、关键架构决策

| 决策 | 结论 |
|---|---|
| 课程模型 | 直接新建 `courses` 限界上下文；项目不创建 `teams` 业务表 |
| 三端是否同一 SPA | 否。三个独立网页应用和静态制品 |
| 三端是否三套后端 | 否。共享领域后端与数据库，通过 portal + object scope 隔离 |
| 教师是否全局角色 | 教师是平台资格，具体教学权来自课程任职 |
| 学生是否固定角色 | 账号默认可进用户端；课程学习权来自有效选课 |
| 管理员能否审核实验 | 不能；只能监管和异常处置 |
| 前端如何共享 | 仅共享 UI、API、认证/事件客户端和工程配置包，不共享业务页面 |
| 会话如何隔离 | 三站点 host-only Cookie，Session 服务端绑定 portal，不设父域 Cookie |
| API 版本 | 本项目首个正式契约为 `/api/v2`；不提供旧 `/api/v1` 兼容层 |
| API 滚动发布 | 同一 `/api/v2` 在三端滚动窗口内只做向后兼容扩展；破坏性变更必须启用新 major path 或新旧 revision 并存 |
| 入口分层 | Nginx 作为入口与静态层，API Gateway 负责 API 级治理；两层不重复做对象授权 |
| 机器 API 入口 | `api.example.edu` 只建立 integration principal，不设置或伪造 `X-Portal` |
| 运行时 | Swarm 管理平台服务；实验运行时通过受控 adapter，禁止 Web 直连 Docker Socket |
| 日志 | stdout 结构化日志经采集器写 MongoDB；审计事实仍写 MySQL AppendOnly 表 |
| 状态服务 | MySQL、Redis、MongoDB、MinIO 必须分别定义 HA、持久化、备份和恢复验收 |
| 分析事实 | MySQL 业务事实异步生成 analytics 投影；MongoDB 运行日志不能直接充当教学分析库 |
| 相似度结果 | 只能作为教师审核辅助信号，不能自动判定抄袭或自动退回 |
| 学习推荐 | 基于已完成任务、先修关系和可解释规则生成；不能自动选课或改变任务状态 |
| 外部集成 | 首期只做 OIDC、开放 API 和签名 Webhook，明确不做 Moodle/Canvas/LTI 专用连接器 |

## 九、绿地实现基线

- 后端按本目录从空 Django 项目建立 `core/accounts/courses/...` 应用，不创建 `teams` 应用。
- 前端直接建立 `user-web`、`teacher-web`、`admin-web` 三个构建入口，不保留单 SPA 入口。
- MySQL、Redis、MongoDB、MinIO、Swarm 集群均以本项目专用的空环境初始化；禁止导入旧业务数据。
- OpenAPI、数据库 schema、网关路由和前端类型从本目录首次生成，发布前冻结 revision。
- Nginx、API Gateway、Django、Worker、采集器和数据服务先在预发布环境完成真实链路验收，再部署生产。

## 十、待产品确认

1. 新课程默认选课模式是 `OPEN` 还是 `APPROVAL`；邀请码能力已确定进入首期。
2. 实验截止后的延期、补交和逾期成果可见规则。
3. API Gateway 选型（APISIX、Kong、Traefik 或现有网关能力）及是否由 Nginx 终止 TLS。
4. Docker Swarm 是否调度学生实验容器；若实验包含 VM，VM 集群与 Swarm 的边界是什么。
5. MySQL、Redis、MongoDB、MinIO 是部署在 Swarm 中还是使用外部/托管服务，分别接受何种 RPO/RTO。
6. MongoDB 运行日志保留期、可检索字段、合规删除和单月日志容量上限。
7. Agent 向量/混合检索引擎、索引重建方式和容量预算。
8. 相似度支持的成果类型、证据展示阈值与保留期。
