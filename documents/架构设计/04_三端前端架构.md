# 04 三端前端架构

> 上游：`00_架构总纲.md`、`02_后端应用结构与API契约.md`  
> 状态：绿地（greenfield）目标前端设计；三个应用从空入口建立

## 一、核心决策

v2 使用三个独立 React SPA：

- 三个入口和 `index.html`。
- 三套路由树和导航。
- 三个构建产物、站点和版本号。
- 三套 smoke/E2E、部署与回滚。
- 三个 host-only Session，分别登录和退出。
- 一个 workspace 仓库、统一工程规范和有限共享包。

不采用微前端运行时。三个应用不需要在浏览器中互相加载 remote bundle；这会引入版本协商和故障传播，却不能替代后端权限。

```text
│  │  └─ src/{app,routes,features}/
│  └─ admin-web/
│     ├─ index.html
│     ├─ vite.config.ts
│     └─ src/{app,routes,features}/
└─ packages/

   ├─ auth-client/                      # Session/CSRF/错误处理
   ├─ event-client/                     # SSE/续传/去重/降级
   ├─ query-keys/                       # 共享 key 构造规范，不含页面状态

```

### 依赖方向

```text
apps/* → packages/{ui,api-client,auth-client,event-client,query-keys}
packages/* 之间只按明确公开入口依赖
packages/* 不得反向引用 apps/*
一个 app 不得引用另一个 app 的 src
```

`ui` 只承载无业务语义组件和 token，不包含“审核通过按钮”“课程成员表”等业务组件。业务组件留在所属 app，避免管理端能力被共享进用户端。

## 六、身份启动流程

每个应用启动均执行：

```text
加载静态配置
 → GET /api/v2/auth/csrf（无 CSRF Cookie 时）
 → GET /api/v2/me
 → 401：跳本站 /login
 → 403 PORTAL_ACCESS_DENIED：清理本站会话并显示无准入页
 → 200：初始化 SessionProvider、eligible_portals、权限摘要
 → 建立本站 SSE
```

`GET /me` 返回：

```json
{
  "data": {
    "public_id": "01...",
    "display_name": "...",
    "portal": "TEACHING",
    "eligible_portals": ["USER", "TEACHING"],
    "account_status": "ACTIVE",
    "teacher_qualification": "ACTIVE",
    "permissions": ["course.create"],
    "course_scopes": [{"course_id": "01...", "role": "OWNER"}]
  },
  "meta": {"trace_id": "..."}
}
```

`course_scopes` 只用于导航/选择器，不代表后端已授权未来请求。列表大时返回摘要并分页获取，不把全量名册/权限塞进 Session。

跨站入口是普通链接。目标站没有 Session 时显示自己的登录页，不从来源站读取 token/localStorage 或通过 URL 传凭证。

## 七、HTTP 与状态管理

### Server state

使用 TanStack Query。query key 必须包含 portal 隐含边界和 course：

```text
['me']
['courses', 'catalog', filters]
['enrollments', 'mine', filters]
['teaching', 'course', courseId]
['teaching', 'enrollments', courseId, filters]
['tasks', portal, courseId, filters]
['platform', 'instances', filters]
```

登出、portal mismatch、资格撤销时清空整个 QueryClient；课程 grant 变化时清除对应 course keys。

### Client state

仅保留主题、表格列、未提交表单和工作区布局。审核结果、课程状态、选课状态、实例状态、归档结果不放全局客户端 store 作为事实。

### HTTP client

共享 `auth-client` 负责相对路径请求、CSRF、统一错误、trace_id、`If-Match`、幂等键重放。三个 app 不把 Session/token 写入 localStorage。幂等键在一次用户意图的重试期间保持相同，请求体改变时必须生成新键。

## 八、SSE 与缓存同步

每个应用只订阅本站允许的事件。事件处理以失效 query 为主，不在多个页面手工复制服务端状态：

```text
enrollment.activated → invalidate 我的课程/教师名册
task.assigned → invalidate 我的实验/课程进度
task.status_changed → 更新任务详情或 invalidate 列表
review.decided → invalidate 任务结果/审核队列
platform.alert → invalidate 管理端总览
```

按 event id 去重，使用 `Last-Event-ID` 重连；超过可恢复窗口时全量刷新。SSE 断开显示连接状态但不阻止已确认的普通读写，不能假装任务成功。

## 九、UI 与响应式边界

- 三站点共享品牌 token、表单、表格、Dialog、Toast、Badge、空态和错误页。
- 用户端面向高频实验流程，支持 1440/920/390px；实验室用独立全屏布局。
- 教师端/管理端是桌面操作台，以 1280+ 优化，920px 仍可完成核心工作。
- 小屏上的复杂管理表格使用字段优先级、抽屉详情或明确的“请使用桌面完成此操作”，不能横向溢出遮挡按钮。
- 课程、实验和对象必须显示真实状态；颜色只作辅助，必须有文本/图标语义。
- 危险操作用确认 Dialog，展示对象、影响、阻断和审计原因；不能以 Toast 代替确认。
- 三站点可有不同信息密度，但不得复制三套不一致的状态文案；枚举标签来自共享生成层/固定映射包。
- 本期不实现 PWA、离线通知或独立移动端只读模式；现有 IndexedDB 自动保存只用于实验内容容错，不把网页包装成离线应用。
- 本期不建设多语言切换或专项无障碍合规功能；仍需保持基本语义 HTML、键盘可操作性和无布局遮挡，作为常规质量要求而非独立产品模块。

## 十、构建、部署与版本

每个应用独立命令：

```text
npm run build:user
npm run build:teacher
npm run build:admin
npm run test:e2e:user
npm run test:e2e:teacher
npm run test:e2e:admin
```

输出目录独立，静态文件使用内容 hash。每个应用在构建时写入 `APP_VERSION` 和 `OPENAPI_REVISION`，错误报告携带版本。公共包变更只触发受影响应用的测试/构建，但合并门禁至少验证三端 typecheck 和 API import 边界。

三个应用都从同一冻结的 `/api/v2` OpenAPI revision 生成客户端。滚动发布只允许兼容性扩展：先发布兼容旧客户端的后端与网关，再分别发布三端，确认旧制品退出后才移除弃用字段。破坏性变更必须使用新 major path 或双 revision 并存。任一网页可独立回滚到仍处于后端兼容窗口内的制品。

生产流量统一经过 Nginx 和 API Gateway：

```text
user.example.edu       ─┐
teacher.example.edu     ├─ Nginx：TLS/静态/Host 路由 ─ API Gateway ─ Django
admin.example.edu      ─┘
api.example.edu（无前端） ─ Nginx/Gateway ─ integration token/open API ─ Django
```

Nginx 为三个网页站点提供独立静态根目录；带内容 hash 的 JS/CSS 可长期缓存，`index.html` 必须短缓存或 `no-cache`。`/api/v2`（包括 SSE）、`/workspace`、`/files` 不由静态站点兜底。`api.example.edu` 不提供静态根目录，只允许机器 token/open API 路由。API Gateway 路由和前端制品分别版本化，网关变更必须同时通过三端与 external-api 契约检查。

每个站点的部署制品至少包含 `APP_VERSION`、`OPENAPI_REVISION`、构建时间和 Git revision；错误页显示版本但不显示内部节点信息。发布前执行静态资源完整性、CSP、SSE/WS 代理、Cookie host-only 和 OpenAPI revision 检查。

## 十一、本地开发

推荐本地域名：

```text
http://user.localhost:5173
http://teacher.localhost:5174
http://admin.localhost:5175
```

各 Vite server 将 `/api`、`/workspace` 和 `/files` 代理到本地入口；SSE 使用 `/api/v2/events/stream`，不再设置独立 `/events` API 前缀。使用不同 hostname 而不只是不同端口，因为 Cookie 不按端口隔离。生产可信 `X-Portal` 只能由网关注入，开发代理配置不能带入生产。机器 API 使用单独的 `api.localhost` 入口和 IntegrationPrincipal，不复用任一 portal。

## 十二、测试门禁

| 层 | 三端要求 |
|---|---|
| 单元 | query key、表单、状态映射、事件去重、权限体验守卫 |
| 契约 | 生成类型无 diff 漏审；app 禁止导入不属于自己的 API 分组 |
| 组件 | loading/empty/error/403/409/412/异步状态 |
| E2E | 每端登录、核心旅程、跨端拒绝、资格撤销、Session portal mismatch |
| 安全 | localStorage 无凭证、CSP、父域 Cookie 不存在、跨站 URL 不带 token |
| 视觉 | 1440/920/390 用户端；1440/920 教师/管理端，无文本/操作遮挡 |
| 交付 | 三个应用分别 smoke、发布、回滚；一个站点故障不影响另外两个静态站点 |

本地和预发布环境也要覆盖 Nginx → API Gateway → Django 的真实链路；仅绕过网关访问 Django 的测试不能证明 portal 头、SSE、工作区和限流配置正确。
