# 07 模块拆分与并行开发任务

**版本：** v1.0  
**状态：** 待审核的候选开发基线  
**团队配置：** 5 人：1 名项目经理、3 名后端开发（按三条责任流分工并按域切片承担前端页面）、1 名测试兼运维；不设专职前端，不记录具体人员姓名与兼任安排

## 1. 并行开发原则

以 OpenAPI、数据库迁移边界、事件 Schema、Fake RuntimeAdapter 和 UI v1.0 页面清单建立并行边界。G1 冻结前只能开发工程骨架、页面壳、Mock 和测试夹具；G1 通过后进入业务联调。后端按三条长期责任流分工，同一责任流内的任务顺序交付，不将同一人的两个任务计作并行产能。

## 2. 任务包和责任分配

| 编号 | 模块 | 主要交付物 | 前置依赖 | 责任人 | 可并行组 |
|---|---|---|---|---|---|

后端按责任流顺序推进：后端 1 负责 `M1 -> M4-B -> M6`，后端 2 负责 `M2 -> M5`，后端 3 负责 `M3 -> M4-A`。M4-A 与 M4-B 可并行，但 M3 与 M4-A、M1 与 M4-B/M6、M2 与 M5 均不能按完全并行估算。M7 与 M8 由对应后端按域切片顺序完成：先用户端主链路，再教学/管理端；项目统筹不得挤占权限、归档和回收等 P0 安全门禁。

## 3. 阶段依赖

```text
后端1：M1 平台基础 -> M4-B 工作区网关 -> M6 Agent
后端2：M2 模板任务 ----------------> M5 报告审核归档
后端3：M3 编排/容器 -> M4-A 虚拟机 ------> 生命周期联调

测试运维：M9 持续提供 CI、Mock、测试环境和质量门禁
前端切片（后端按域承担）：G1 Mock/OpenAPI -> M7 用户端 -> M8 教学/管理端
```

- G1 阶段三名后端并行产出：后端 1 完成 M1 骨架和公共契约，后端 2 完成 M2 Schema/Mock，后端 3 完成 M3 RuntimeAdapter/Fake Adapter。
- G1 后 M2 与 M3 并行；M3 的适配器和编排骨架冻结后，后端 3 再进入 M4-A。后端 1 在身份和会话契约冻结后进入 M4-B，再进入 M6。
- M5 在 M2 主流程完成后由后端 2 接续实现；开发期间使用 M3/M4 的实例、快照、会话和销毁 mock，不等待全部真实运行时完成。
- M7 可在 G1 后立即使用 Mock 开发页面壳和状态组件；业务联调必须等待相关 API 契约冻结。
- M8 依赖模板、任务、审核、运行时和补偿接口 mock；先做只读列表和页面壳，后接写操作。
- M9 从第一天开始，阶段性接入每个模块的测试和观测，不在最后集中补测试。

## 5. 每个任务包完成定义

1. 有 OpenAPI/事件 Schema、数据库迁移、权限矩阵、错误码和数据脱敏说明。
2. 有单元、接口、契约和关键失败路径测试；写操作有幂等/并发测试。
3. 在测试环境用种子数据完成冒烟，不依赖开发者本机手工配置。
4. 能按 `request_id`/`trace_id`/业务 ID 定位一次成功或失败。
5. 有 README、运行/回滚说明、演示脚本和追踪矩阵链接。
6. 通过代码评审、质量门禁和至少一次跨模块演示后才能标记完成。
